# 短链服务跳转链路压测报告

> 测试时间：2026-11-09
> 被测应用：shortlink（Spring Boot 3.5.7 + MyBatis-Plus + MySQL 8 + Redis 7）
> 附：JMeter 脚本与三组按 5 秒聚合的明细数据在同目录 `loadtest/` 下，原始 `.jtl` 因体积原因未入库（见“附件”一节）

## 一、测试目标

验证三级方案对跳转接口（`GET /{code}`）吞吐与延迟的影响：

1. 直连 MySQL
2. 单级 Redis 缓存
3. Caffeine + Redis 两级缓存

## 二、测试环境

| 项 | 配置 |
|---|---|
| 机器 | 本机（Windows，Docker Desktop） |
| 应用 | Spring Boot 3.5.7，内嵌 Tomcat，JVM 21 |
| MySQL | Docker `mysql:8.0`，端口 3307，表内数据量 12 行 |
| Redis | Docker `redis:7`，端口 6379 |
| 压测工具 | Apache JMeter 5.6.3，无界面模式（`-n`） |
| 并发 | 200 线程，爬坡 5 秒，持续 60 秒 |
| 目标接口 | `GET http://localhost:8080/9`（已存在的短码） |
| 重定向 | JMeter `follow_redirects=false`，只统计 302 响应本身 |

**每组开始前执行 `redis-cli flushall` 清空缓存**，避免上一组残留数据影响结果。

## 三、测试方法

在 `application.yml` 中通过开关切换缓存层级，重启应用后压测：

```yaml
shortlink:
  cache:
    l1-enabled: true    # Caffeine 本地缓存
    l2-enabled: true    # Redis 缓存
```

| 组别 | l1-enabled | l2-enabled |
|---|---|---|
| ① 直连 DB | false | false |
| ② 单级 Redis | false | true |
| ③ 两级缓存 | true | true |

压测命令（在项目根目录执行）：

```powershell
jmeter -n -t docs/loadtest/shortlink-test.jmx -l run.jtl -Jjmeter.save.saveservice.output_format=csv
```

## 四、测试结果

| 组别 | 请求总数 | QPS | 平均延迟 | P50 | P99 | 最大延迟 | 错误率 |
|---|---|---|---|---|---|---|---|
| ① 直连 DB | 315,337 | 5,256 | 36 ms | 37 ms | 86 ms | 199 ms | 0.00% |
| ② 单级 Redis | 795,136 | 13,252 | 14 ms | 14 ms | 21 ms | 283 ms | 0.00% |
| ③ 两级缓存 | 1,042,569 | 17,376 | 11 ms | 11 ms | 18 ms | 136 ms | 0.00% |

**提升幅度**

| 对比 | QPS 提升 | P99 变化 |
|---|---|---|
| ① → ② | 2.52 倍 | 86 → 21 ms（-76%） |
| ② → ③ | 1.31 倍 | 21 → 18 ms（-14%） |
| ① → ③ | 3.31 倍 | 86 → 18 ms（-79%） |

## 五、结论与分析

**1. 缓存是跳转链路的主要瓶颈所在**

直连 DB 时，每次跳转都要一次主键/唯一索引查询，QPS 卡在 5,256。加 Redis 后提升 2.52 倍，说明数据库是首要瓶颈。

**2. 第二级缓存（Caffeine）收益递减，原因是瓶颈转移**

Caffeine 只提升 31%，因为加 Redis 之后数据库已不再是瓶颈，Tomcat 工作线程、HTTP 报文解析、连接复用成为新的天花板。Caffeine 省掉的仅是一次 Redis 网络往返（约 0.2~0.5 ms），在 11 ms 的整体延迟中占比有限。

这个现象符合**阿姆达尔定律**：优化掉一个瓶颈后，整体收益取决于该环节在总耗时中的占比。

**3. 本次测试的数据口径说明**

- 表内仅 12 行数据且全部驻留 InnoDB buffer pool，直连 DB 的成绩偏乐观，真实场景差距会更大
- 所有请求指向同一个短码，Redis 与 Caffeine 命中率接近 100%，未测试缓存穿透/击穿场景
- 200 并发在本机运行，JMeter 与被测应用争抢 CPU，绝对值仅供参考，**组间相对差异才是有效结论**
- 第 0~5 秒窗口包含 5 秒爬坡期，QPS 明显低于稳态（如组① 4,253 vs 稳态约 5,400），看曲线时属正常现象

## 六、复现步骤

```powershell
# 1. 启动依赖
docker compose up -d

# 2. 清空缓存、切换配置、启动应用
docker exec sl-redis redis-cli flushall
mvn spring-boot:run

# 3. 压测（改 application.yml 开关后重启，重复三次）
jmeter -n -t docs/loadtest/shortlink-test.jmx -l run.jtl -Jjmeter.save.saveservice.output_format=csv
```

## 七、附件

| 文件 | 说明 |
|---|---|
| `loadtest/shortlink-test.jmx` | JMeter 测试计划（200 线程 / 60 秒 / 断言 302） |
| `loadtest/run1-summary.csv` | 组① 按 5 秒聚合：请求数、QPS、平均、P50/P90/P99、最大、错误数 |
| `loadtest/run2-summary.csv` | 组② 同上 |
| `loadtest/run3-summary.csv` | 组③ 同上 |

原始结果 `run1.jtl`、`run2.jtl`、`run3.jtl` 共约 250MB（逐条请求记录），未纳入仓库：既超出 Git 托管平台单文件上限，也会让 clone 变得难以接受。上表与 CSV 中的所有数字均由这三份原始文件聚合得出，聚合方式为按请求时间戳每 5 秒切一个窗口，百分位取最近秩（nearest-rank）。需要逐条数据可按下节步骤自行复现。

## 八、已知局限

- 未做阶梯加压（如 50/100/200/500 并发），看不出拐点
- 未测试写入链路（生成短码）在高压下的表现
- 单机部署，未验证多实例下 Caffeine 本地缓存的一致性问题（这正是 L1 TTL 设为 10 秒、远短于 Redis 30~40 分钟的原因）
