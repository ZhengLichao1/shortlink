# ShortLink 短链服务

> 个人练习项目，非生产可用。用来把缓存、发号、HTTP 重定向这几块串起来。

把长网址转换成短码，访问短链时 302 跳转到原地址，并统计点击量。

技术栈：Spring Boot 3.5 · MyBatis-Plus · MySQL 8 · Redis 7 · Caffeine · Guava · Docker Compose · JMeter

## 为什么要做这个

短链最常见的三个用途：短信按字数计费，70 字里塞不下一条长链；二维码字符越少格子越大、越好扫；
同一个落地页发多条短链，才能区分是哪个渠道带来的访问。

这些场景的共同点是**生成一次、访问上万次**，所以设计的重心放在读取侧——让跳转链路尽量不碰数据库，
写入侧只要保证短码不重复就够了。

选它当练手项目，是因为代码量不大，但缓存穿透/击穿/雪崩、分布式发号、HTTP 重定向语义这几块能
一次串起来，每个点都能往下深挖。这里只是一个本地跑通的练习实现，没做限流、监控和分库，
不能直接用于生产，仅作练习参考；下面的数据也都是本机实测，环境和口径见压测一节。

## 架构

```
                    ┌──────────────────────────────────────────┐
   GET /{code} ───▶ │  ① Caffeine（进程内，TTL 10s）            │ 命中直接返回
                    └──────────────────┬───────────────────────┘
                                       │ 未命中
                    ┌──────────────────▼───────────────────────┐
                    │  ② Redis（TTL 30~40 分钟，随机抖动）       │ 命中回填 L1
                    └──────────────────┬───────────────────────┘
                                       │ 未命中
                    ┌──────────────────▼───────────────────────┐
                    │  ③ 布隆过滤器                             │ 判定不存在 → 直接 404
                    └──────────────────┬───────────────────────┘
                                       │ 可能存在
                    ┌──────────────────▼───────────────────────┐
                    │  ④ 互斥锁（Redis SETNX）                  │ 只放一个请求进去
                    └──────────────────┬───────────────────────┘
                                       │
                    ┌──────────────────▼───────────────────────┐
                    │  ⑤ MySQL 回源，结果写回 ①②               │
                    └──────────────────────────────────────────┘
```

## 核心设计

### 短码生成：号段发号 + Base62

不用自增主键（会暴露数据量、分库后不唯一），也不用哈希取模（要处理碰撞）。

`SegmentIdGenerator` 一次向 Redis 申请 1000 个号存在本地，发号时纯内存自增：

- Redis 往返从「每号一次」降到「每千号一次」
- 当前号段没发完时，Redis 短暂不可用也能继续发号
- 短码字段建唯一索引兜底，理论上不会撞，撞了也会被数据库拦下

### 三级防护

| 问题 | 手段 |
|---|---|
| **穿透**（查不存在的短码） | 布隆过滤器拦截 + 1 分钟空值缓存 |
| **击穿**（热点 key 失效瞬间大量请求） | 回源前抢 Redis 互斥锁（`SET NX PX`，Lua 比对 token 后释放），只放一个请求查库 |
| **雪崩**（大量 key 同时过期） | TTL 加 0~10 分钟随机抖动 |

布隆过滤器在启动时预热全量短码（`BloomFilterWarmup`），新建短码时同步写入。
它只有假阳性没有假阴性——说「不存在」就一定不存在，所以拿来挡穿透是安全的。

### 两级缓存的取舍

| | Caffeine | Redis |
|---|---|---|
| 延迟 | 纳秒级 | 约 0.2~0.5 ms |
| 共享范围 | 单进程 | 跨实例 |
| TTL | **10 秒** | 30~40 分钟 |

**L1 的 TTL 故意设得很短**：本地缓存没有失效通知机制，多实例部署时 A 实例改了数据，
B 实例的本地缓存还是旧的，只能等它自然过期。用短 TTL 换取「脏数据最多存在 10 秒」。

### 跳转链路不写数据库

点击量用 Redis `INCR` 累加，同时把短码扔进一个 dirty set；定时任务每 30 秒批量刷回数据库。

好处是不用在跳转时 `UPDATE t_link SET click_num = click_num + 1` —— 热门短链的所有请求
会争抢同一行记录的行锁，写入会变成瓶颈。

落库后可查累计点击量。注意这里只有 PV，不区分 UV（没有存访问明细，分不出“1 人点 100 次”和“100 人各点 1 次”）：

```sql
select short_uri, click_num from t_link order by click_num desc limit 10;
```

## 压测结果

JMeter 5.6.3，200 并发、爬坡 5 秒、持续 60 秒，压测对象为已存在的短码（`GET /9`），每组开始前执行 `flushall`。
测试机为本机（Windows + Docker Desktop），JMeter 与被测应用争抢同一份 CPU，绝对值仅供参考。

| 组别 | QPS | 平均延迟 | P99 | 错误率 |
|---|---|---|---|---|
| ① 直连 DB | 5,256 | 36 ms | 86 ms | 0% |
| ② 单级 Redis | 13,252 | 14 ms | 21 ms | 0% |
| ③ Caffeine + Redis | **17,376** | **11 ms** | **18 ms** | 0% |

**加 Redis 提升 2.52 倍，再加 Caffeine 只提升 1.31 倍。**

第二级收益递减的原因是**瓶颈转移**：加 Redis 后数据库不再是瓶颈，Tomcat 工作线程和
HTTP 解析成了新天花板；Caffeine 省掉的只是 0.2 ms 的网络往返，在 11 ms 的总延迟里占比有限。

> 数据口径说明：表内仅十几行且全在 buffer pool，直连 DB 的成绩偏乐观；所有请求打同一个
> 短码，命中率接近 100%，未覆盖冷启动场景。**相对差异比绝对值更可信。**

完整报告见 [docs/压测报告.md](docs/压测报告.md)，JMeter 脚本和三组按 5 秒聚合的明细数据
（QPS、P50/P90/P99 随时间变化）在 `docs/loadtest/` 下，可据此自行复现。

## 快速开始

环境要求：JDK 21、Docker Desktop。

```bash
# 1. 启动 MySQL(3307) 和 Redis(6379)
cp .env.example .env      # 填写 MYSQL_ROOT_PASSWORD
docker compose up -d

# 2. 准备应用本地配置（不入库），密码与上一步保持一致
cp src/main/resources/application-local.yml.example src/main/resources/application-local.yml

# 3. 启动应用（默认 8080）
mvn spring-boot:run
```

浏览器打开 `http://localhost:8080`，有单页演示界面，粘贴长链即可生成并复制短链。

数据库密码通过 `application-local.yml` 或环境变量 `DB_PASSWORD` 提供，两者都不进仓库：
`.env` 只服务于 Docker 容器，Spring Boot 不读它，应用侧的密码必须由 profile 文件或环境变量给出。

生成短链：

```bash
curl -X POST "http://localhost:8080/api/links?url=https://example.com/very/long/path"
# {"code":"1If","shortUrl":"http://localhost:8080/1If"}
```

访问短链：

```bash
curl -i http://localhost:8080/1If
# HTTP/1.1 302, Location: https://example.com/very/long/path
```

## 已知问题

1. **号段与数据库可能错位**：号段存在 Redis，如果 Redis 被 `flushall` 或回滚，
   发号会从头开始，撞上已有短码。更稳的做法是用数据库自增表或 Redis 持久化 + 业务校验。
2. **点击量可能丢**：Redis 累加后每 30 秒刷盘，服务崩溃会丢掉最多 30 秒的计数。
   对统计精度要求高的场景应改用消息队列。
3. **L1 多实例不一致**：本地缓存靠 TTL 自然过期，最多脏 10 秒。规模上来后
   可以引入 Redis Pub/Sub 广播失效通知。
4. **无自定义短码/有效期**：表里有 `del_flag` 字段，但没做删除和过期接口。
5. **无接口文档**：接口很少，上面的 curl 示例基本够用。
